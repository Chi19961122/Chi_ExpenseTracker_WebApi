# Chi.ExpenseTracker 重構說明（2026-07-10）

> 本文件記錄 `feature/Ai-Refactor` 分支的全面重構：從舊架構 `Chi_ExpenseTracker_*` 遷移到新架構 `Chi.ExpenseTracker.*`。
> 前半部以**企劃（PM）視角**說明「為什麼要改、對產品與使用者的影響」；後半部以**工程師視角**說明「改了什麼、怎麼改、如何接手」。

---

## TL;DR

| | 舊版 | 新版 |
|---|---|---|
| 安全性 | 任何登入者可讀寫**他人**的帳目；DB 密碼與 JWT 金鑰進了版控 | 資料一律以 JWT 身分隔離；機密移出版控 |
| 穩定性 | 登入打錯帳號直接系統錯誤（500）；編輯交易會把日期洗掉 | 已知 bug 全數修復，統一錯誤處理 |
| API 風格 | 動詞式路由、永遠回 200、自訂錯誤碼字串 | RESTful 路由、標準 HTTP 狀態碼、ProblemDetails |
| 架構 | 分層錯位（資料層放 Web 設定）、Service Locator | 四層專案、建構子注入，比照 Chi.TradeLog 規範 |
| 技術 | .NET 8、EF Core + Dapper、Autofac | .NET 10、EF Core 10、內建 DI、FluentValidation、AutoMapper |
| 測試 | 1 個單元測試 | 19 個單元測試 + 端到端煙霧測試 |

**資料庫 schema 完全不變**，既有資料直接沿用；但 **API 介面為 breaking change，前端需配合改接**（對照表見下文）。

## 一、企劃視角：為什麼要做這次重構

### 1. 我們解決了什麼風險

| 風險 | 舊版行為 | 影響 | 新版行為 |
|---|---|---|---|
| 🔴 越權存取（最嚴重） | 查詢/修改/刪除資料時，「這是誰的資料」由呼叫端自己聲明（`userId` 參數） | 任何註冊使用者改一個數字，就能看到、改掉、刪除**別人**的記帳資料 | 使用者身分一律由登入權杖（JWT）判定，API 不再接受外部傳入的 userId |
| 🔴 機密外洩 | 資料庫帳密、JWT 簽章金鑰寫死在設定檔並提交進 Git | 拿到原始碼的任何人可直接連正式資料庫、偽造任何人的登入權杖 | 機密改由本機 User Secrets／部署環境變數提供；正式環境若誤用開發金鑰，服務會直接拒絕啟動 |
| 🟡 密碼回傳 | 註冊成功後，API 把使用者輸入的明文密碼原樣回傳 | 密碼暴露在網路回應與瀏覽器紀錄中 | 回應只含使用者基本資料，永不含密碼 |
| 🟡 全域跨域開放 | 任何網站都能呼叫本 API | 惡意網站可掛使用者的憑證發請求 | 僅允許白名單來源（本機開發 + netlify 正式站） |

### 2. 我們修好了什麼（使用者有感的錯誤）

- **登入打錯帳號會看到「系統錯誤」**：現在正確回覆「帳號或密碼錯誤」。
- **編輯一筆交易後，交易日期消失／報錯**：舊版更新時會把日期欄位洗成無效值導致失敗；現在編輯功能完整可用，日期可正常修改。
- **憑證有效期過長**：登入權杖從 12 小時縮短為 1 小時，前端可在到期前呼叫換發（refresh）延長工作階段，兼顧安全與體驗。

### 3. 對使用者與前端的影響

- **既有帳號與記帳資料完全保留**（資料庫結構未變動）。
- 上線後**所有使用者需重新登入一次**（權杖格式與發行者已更新）。
- **前端需要一次性改版**配合新 API（已確認前端會同步修改）：
  - 呼叫路徑與方法改變（見工程段落的 API 對照表）。
  - 所有請求不必再帶 `userId`。
  - 回應格式從「包一層信封」改為「直接回資料」，錯誤改看 HTTP 狀態碼。

### 4. 這次投資換到什麼

- **可維護性**：分層清楚、相依明確，新功能（如 Future 清單中的預算管理、報表）可以在不動基礎的前提下疊加。
- **可測試性**：核心邏輯已有 19 個自動化測試護航，日後改動能快速驗證不破壞既有行為。
- **一致性**：與 Chi.TradeLog 採用同一套規範，兩個專案之間的經驗與程式碼可以互相移植。

## 二、工程師視角：改了什麼、怎麼改

### 1. 專案結構對照

```
舊                                          新
Chi_ExpenseTracker_WebApi.sln               Chi.ExpenseTracker.sln
Chi_ExpenseTracker_WebApi/                  src/Chi.ExpenseTracker.Api/
Chi_ExpenseTracker_Service/                 src/Chi.ExpenseTracker.Services/
Chi_ExpenseTracker_Repesitory/  (拼字誤)    src/Chi.ExpenseTracker.Repositories/
（無）                                      src/Chi.ExpenseTracker.Common/
Chi_ExpenseTracker_UnitTest/                tests/Chi.ExpenseTracker.Tests/
```

分層職責重新劃定：

| 層 | 舊版問題 | 新版職責 |
|---|---|---|
| Api | Controller 手動複製回應信封；Swagger/CORS/JWT/IoC 設定散落在**資料層** | Controller、Parameter/ViewModel、FluentValidation、例外處理 middleware、`Program.cs` 集中組態 |
| Services | 回傳 `ApiResponseModel`（混入 HTTP 概念）；Service Locator 取相依 | 純業務邏輯，回傳 DTO 或 null（not-found），建構子注入 |
| Repositories | 泛型 `DbBase` 混用 EF Core + Dapper + BulkExtensions，`Db` 泛型參數形同虛設 | 依聚合（Users/Categories/Transactions）拆明確介面，EF Core 10 全 async |
| Common（新增） | — | `JwtOptions`、跨層 DTO/InfoModel，避免 Api 與 Services 互相耦合 |

### 2. 關鍵設計變更

**(a) 身分識別：Service Locator → JWT claims**

```csharp
// 舊：每個端點自帶 userId（可偽造）
public ApiResponseModel GetAllTransactions(int userId) { ... }

// 新：ApiControllerBase 統一從 JWT sub claim 解析
protected int CurrentUserId => int.TryParse(User.FindFirstValue("sub"), ...);
```

JWT 內容：`sub`＝UserId、`email`、`name`、`role`；`MapInboundClaims = false` 保留原始 claim 名稱。Repository 層所有查詢一律以 `UserId` 過濾，服務層對「更新/刪除不屬於自己的資料」回傳 null/false → API 回 404，外部無法探測他人資料是否存在。

**(b) 相依注入：`IServiceProvider.GetService<T>()` → 建構子注入**

移除 Autofac 組件掃描，改用內建 DI + 兩個擴充方法：`AddApplicationServices()`（Services 層）、`AddDatabaseInfrastructure(connectionString)`（Repositories 層）。相依關係在建構子簽章上一目瞭然，測試時直接 mock 介面。

**(c) 回應格式：自訂信封 → HTTP 語意**

```jsonc
// 舊：HTTP 永遠 200，錯誤藏在自訂欄位
{ "code": "400-001", "msg": "Wrong Username Or Password", "data": { ... } }

// 新：成功直接回資料；錯誤回標準狀態碼 + ProblemDetails
// 401 Unauthorized / 404 Not Found / 409 Conflict / 400：
{ "title": "One or more validation errors occurred.", "status": 400,
  "errors": { "Email": ["電子郵件格式不正確"] } }
```

未攔截例外由 `ExceptionHandlingMiddleware` 統一記 log 並回 500 ProblemDetails，不再把例外堆疊外洩給呼叫端。

**(d) Refresh Token 機制簡化**

舊版把 refresh token（本身也是 JWT）明文存於 `Users.RefreshToken` 欄位並以字串比對。新版比照 Chi.TradeLog：**持有效 access token 呼叫 `POST /api/auth/refresh` 即可換發新權杖**，不再落地儲存。`Users.RefreshToken` 欄位已停用（見資料庫章節）。

**(e) 已修復的程式缺陷**

| 缺陷 | 根因 | 修法 |
|---|---|---|
| 登入不存在帳號 → 500 | `BCrypt.Verify` 前未檢查 user 為 null | `user is null || Verify(...) is false` 短路 |
| 編輯交易把 CreateDate 洗成 0001-01-01（SQL datetime 溢位） | `DbBase.Update` 將整個 detached entity 標記 Modified、未帶的欄位覆寫成預設值 | 改為「先載入追蹤實體 → 逐欄位更新 → SaveChanges」，日期由參數明確提供 |
| 註冊回傳明文密碼 | 直接把輸入 DTO 放回 `result.Data` | 回傳 `UserDto`（無密碼欄位） |
| 換類別時未驗證所有權 | 建立/編輯交易可掛到任何 CategoryId | 服務層先確認類別屬於當前使用者，否則 404 |
| Email 大小寫視為不同帳號 | 直接字串比對 | 註冊/登入前一律 `Trim().ToLowerInvariant()` |

### 3. API 對照表（前端改接指南）

所有受保護端點需帶 `Authorization: Bearer <token>`；**不再傳 userId**。

| 舊 | 新 | 成功回應 | 失敗回應 |
|---|---|---|---|
| `POST /Auth/Register` | `POST /api/auth/register` | 201 + UserViewModel | 400 驗證、409 Email 重複 |
| `POST /Auth/Login` | `POST /api/auth/login` | 200 + `{token, user}` | 400 驗證、401 帳密錯誤 |
| `POST /Auth/RefreshToken` | `POST /api/auth/refresh`（body 免帶） | 200 + `{token, user}` | 401 |
| `GET /Category/GetCategories?userId=&type=` | `GET /api/categories?type=` | 200 + 陣列 | — |
| `POST /Category/CreateCategories` | `POST /api/categories` | 201 + CategoryViewModel | 400 |
| `POST /Category/EditCategories` | `PUT /api/categories/{id}` | 200 + CategoryViewModel | 400、404 |
| `DELETE /Category/DeleteCategoryById?userId=&categoryId=` | `DELETE /api/categories/{id}` | 204 | 404 |
| `GET /Transaction/GetAllTransactions?userId=` | `GET /api/transactions` | 200 + 陣列（含 categoryName/categoryType） | — |
| `GET /Transaction/GetTransactionsById?...` | `GET /api/transactions/{id}` | 200 + TransactionViewModel | 404 |
| `POST /Transaction/CreateTransactions` | `POST /api/transactions` | 201 + TransactionViewModel | 400、404（類別無效） |
| `POST /Transaction/EditTransactions` | `PUT /api/transactions/{id}` | 200 + TransactionViewModel | 400、404 |
| `DELETE /Transaction/DeleteTransactions?...` | `DELETE /api/transactions/{id}` | 204 | 404 |

請求/回應範例：

```jsonc
// POST /api/auth/login
{ "email": "test@example.com", "password": "******" }
// → 200
{ "token": "eyJ...", "user": { "userId": 1, "userName": "Test", "email": "test@example.com", "role": "User" } }

// POST /api/transactions
{ "categoryId": 3, "amount": 120, "createDate": "2026-07-10", "description": "午餐" }
// → 201
{ "transactionId": 32, "categoryId": 3, "categoryName": "餐飲", "categoryType": "Expense",
  "amount": 120, "createDate": "2026-07-10T00:00:00", "description": "午餐" }
```

欄位驗證規則（400 時 `errors` 會逐欄回覆繁中訊息）：Email 需為合法格式；密碼 6–72 字；類別名稱必填 ≤50 字、型態限 `Expense`/`Income`、圖示 ≤5 字；交易需選類別、金額 >0、日期必填、備註 ≤250 字。

### 4. 技術棧與套件變更

| 項目 | 舊 | 新 |
|---|---|---|
| Target Framework | net8.0 | net10.0 |
| ORM | EF Core 8.0.6 + Dapper 2.1.35 + EFCore.BulkExtensions | EF Core 10.0.2（單一資料存取技術） |
| DI | Autofac 8（組件掃描） | 內建 DI + 擴充方法顯式註冊 |
| 驗證 | 無 | FluentValidation 11.11 |

| 測試 | xUnit + NSubstitute | xUnit + NSubstitute + FluentAssertions |
| 移除 | `WeatherForecast` 範本、`RNGCryptoServiceProvider` 死碼、註解掉的程式碼、`ApiCodeEnum`（含前案殘留的 Order 錯誤碼） | — |

### 5. 資料庫相容性

- **Schema 未變動**：Entity 與 DbContext（`_ExpenseDbContext` → `ExpenseDbContext`）只改了型別/命名空間，資料表對應完全相同。
- **Migrations 原樣搬移**：Migration Id 不變，`__EFMigrationsHistory` 相容；僅更新 namespace 與 snapshot 內的型別名稱字串。
- **`Users.RefreshToken` 欄位已停用**：程式不再讀寫；snapshot 保留該欄位，**下一次 `dotnet ef migrations add` 會自動產生 DropColumn**。
- ⚠️ 既知技術債：migrations 歷史只涵蓋 Users 表（Categories/Transactions 當初為 DB-first 手動建立），snapshot 與實際 model 不同步。若日後要以 migrations 管理 schema，需先重新 baseline。

### 6. 組態與部署變更

| 設定 | 舊 | 新 |
|---|---|---|
| 連線字串 | `ConnectionStrings:Azure`（含密碼，已進版控） | `ConnectionStrings:Default`；本機用 Windows 驗證寫在 appsettings.Development.json，Azure 連線放 User Secrets／環境變數 |
| JWT | `JwtConfig`＋靜態 `AppSettings` 類別 | `Jwt` 區段 + `IOptions<JwtOptions>`；正式環境若 Key 仍為 `dev-only` 前綴則**啟動即失敗** |
| CORS | `AllowAnyOrigin` | `Cors:AllowedOrigins` 白名單（localhost:5173/8080 + netlify） |
| 認證管線 | 缺 `app.UseAuthentication()`（`[Authorize]` 端點實際上全數 401） | `UseAuthentication` + `UseAuthorization` 順序正確 |
| Swagger | 全環境開放 | 僅 Development（含 Bearer 授權按鈕與 XML 註解） |

本機開發設定機密：

```bash
cd src/Chi.ExpenseTracker.Api
dotnet user-secrets set "ConnectionStrings:Default" "<Azure 連線字串>"   # 需要連 Azure 時
```

部署環境需設定環境變數：`ConnectionStrings__Default`、`Jwt__Key`（≥32 字元隨機字串）。
